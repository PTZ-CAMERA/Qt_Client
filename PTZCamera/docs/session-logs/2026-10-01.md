# 개발 세션 기록 — 2026-10-01

## 오늘 한 일

- Codex CLI에서 현재 폴더의 최근 세션을 다시 여는 명령이 `codex resume --last`임을 확인했다.
- 더 이상 사용하지 않는 ESP32-C6 상태 표시와 메시지 처리 코드를 Qt 클라이언트에서 제거했다.
- PTZ 버튼 외에 키보드 `↑`, `↓`, `←`, `→`로 이동 명령을 보낼 수 있게 했다. `r`과 `R`은 버튼과 동일하게 `PTZ:CENTER`를 보낸다. IP·포트 입력칸을 편집할 때는 키보드 PTZ 명령을 처리하지 않는다.
- Raspberry Pi 영상 연결 후보를 검토했다. 현재 Qt 6.11.0 MinGW 환경에는 Qt Multimedia가 설치돼 있고 Qt WebEngine은 설치돼 있지 않다. 저지연을 우선해 RTSP 영상의 직접 프레임 표시 방식을 선택했다.
- `VideoStreamClient`를 추가해 `rtsp://<IP>:8554/cam`을 `QMediaPlayer`로 열고, `QVideoSink`에서 받은 `QVideoFrame`을 기존 `CameraWidget`에 전달한다. 위젯은 프레임을 직접 그린 후 중심점과 탐지 오버레이를 그린다.
- 영상용 `Start video`/`Stop video` 버튼을 TCP 제어용 `Connect`/`Disconnect` 버튼과 분리했다. 기본 Pi IP는 `192.168.0.92`로 설정했다. TCP 제어의 기본 포트는 `5000`이다.
- 기본 RTSP 하위 전송은 UDP로 설정했다. 실행 전에 `QT_FFMPEG_RTSP_TRANSPORT` 환경 변수를 지정하면 해당 설정을 우선한다.
- 기술 선택과 후보 비교를 [`0001-low-latency-video.md`](../tech-decisions/0001-low-latency-video.md)에 기록했다. 이후 기술 선택도 Markdown으로 남기도록 저장소 루트의 [`AGENTS.md`](../../../AGENTS.md)에 규칙을 추가했다.
- Pi 측에서 WebRTC `http://192.168.0.92:8889/cam/` 응답과 프레임 수신을 다시 확인했다고 전달했다. Qt에서는 RTSP 영상 URL을 직접 바꿀 수 있는 입력칸을 추가하고, WebRTC URL은 외부 브라우저에서 여는 버튼을 추가했다. 두 프로토콜을 같은 포트 변경으로 취급하지 않도록 분리했다.
- 이후 카메라 영역에 WebRTC/RTSP 선택과 내장 재생을 구현하도록 요구가 바뀌었다. `CameraPlaybackWidget`으로 두 방식을 전환하고, RTSP는 TCP 전송과 `QVideoWidget`, WebRTC는 `QWebEngineView`를 사용하도록 코드를 수정했다. WebRTC 내장 빌드에는 MSVC용 Qt WebEngine Kit이 필요하다.

## 확인 결과

- Windows용 Qt 6.11.0 MinGW Kit으로 CMake 구성과 빌드가 성공했다.
- `windeployqt`로 Qt Multimedia, FFmpeg 플러그인과 실행에 필요한 DLL을 빌드 폴더에 배치했다.
- `PTZ Object Tracking Camera` 창이 Windows에서 실행 중인 것을 확인했다.
- Pi의 WebRTC 주소 `http://192.168.0.92:8889/cam/`은 오늘 한 차례 HTTP 200을 반환했으나, 구현 후 재확인에서는 8889와 RTSP 8554 포트가 연결을 거부했다. TCP 제어 포트 5000도 연결을 거부했다. 따라서 실제 영상 표시, PTZ 명령 전달, 종단 간 지연은 아직 확인하지 못했다.
- URL 입력 UI를 추가한 뒤 이 세션의 관리형 샌드박스에서는 Windows CMake 실행이 `UtilBindVsockAnyPort: socket failed 1`로 막혀 새 빌드를 완료하지 못했다. 앞선 빌드 성공은 이 변경 이전의 결과다.
